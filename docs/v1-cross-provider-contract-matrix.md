# V1 cross-provider contract and evidence matrix — provisional

**As of:** 2026-09-17
**Baseline:** commit `0031cc719ab16459f8d20ddcab76fc1d56c285d2` plus the commercial-viability branch changes. This is a **source-tree candidate**, not a tagged, immutable, installed release.
**Purpose:** make P0.7 acceptance measurable while the normative V1 coordination contract is frozen. This matrix does not itself certify any integration or close the Phase 0 release gate.

## Evidence labels

- **Automated:** a named repository test exercises the behavior in an isolated test environment. Passing component tests do not prove an installed provider client can complete the same journey.
- **Live, bounded:** an actual browser/device acceptance is recorded, with its stated OS/client/version and date. It does not establish other platforms or that a subsequently changed binding flow was retested.
- **Unverified:** the required end-to-end, physical-client, or release-artifact exercise has not been recorded. Implemented code alone is not acceptance evidence.

The candidate shared coordination contract is [v1-coordination-contract.md](v1-coordination-contract.md), with HTTP details in [project-api-v1.md](project-api-v1.md) and [openapi-v1.yaml](openapi-v1.yaml). `tests/openapi-message-contract.py` validates 23 real Project API project-list, context, permission-scoped participant, message, page, revision, tombstone, and error responses against the OpenAPI schemas and their 16 operation/status pairs; this is source-tree evidence, not installed-release interoperability. The contract defines project-scoped human/session and agent/bearer authorization, participant identity, canonical message ordering and cursors, direct/mention/broadcast addressees, reply links, and per-addressee acknowledgement. All active project participants may read project messages; addressees indicate responsibility, not exclusive visibility. Acknowledgement is neither proof of first read nor task completion. Notifications are activation hints; the database timeline is authoritative. These shared semantics must be tested through each path, not inferred from a provider adapter's existence.

The companion [provider error and recovery matrix](v1-provider-error-recovery-matrix.md)
separates adapter checks, server/telemetry evidence, and installed-client
outcomes for failure and recovery scenarios.

## Shared contract checks to run through every claimed path

| Check | Existing source-tree evidence | Cross-provider acceptance criterion |
| --- | --- | --- |
| Identity, membership, authorization | `tests/project-api.php` exercises project concealment and rejects foreign addressees/replies; `tests/chatgpt-oauth.php` and Codex plugin tests cover path-specific identity controls. | Every resulting post has the intended project participant; unauthorized/unbound/foreign identities cannot discover or mutate another project. |
| Direct, mention, broadcast responsibility | [project-api-v1.md](project-api-v1.md) defines addressee semantics; `tests/project-api.php` and `tests/agent-activation.php` exercise filtered messages and provider notification paths. | Each addressed participant sees its own responsibility; broadcasts address all other active participants; non-addressees retain project visibility without an acknowledgement right. |
| Reply and exact context | `tests/project-api.php` rejects foreign reply targets; `tests/agent-activation.php` tests the Gemini reply path. The 2026-09-07 live ChatGPT record includes a direct linked reply under the former consent flow. | A reply links to the intended source message in the same project, survives a provider handoff, and is retrievable through every participating path. |
| Acknowledgement | `tests/project-api.php` tests human acknowledgement; `tests/agent-activation.php` tests Gemini's post-then-acknowledge route; MCP exposes `acknowledge_message`. | Only an addressed participant acknowledges its own addressee record, after handling when appropriate; no test or UI calls it completion or first read. |
| Canonical ordering and recovery | [project-api-v1.md](project-api-v1.md) documents newest-first opaque project-bound cursors and one-shot Realtime gap recovery; focused API/Realtime suites exist. | All paths converge on the same message IDs, project sequence, reply relation, and addressee/acknowledgement state after reconnect or delayed wake. | Failure and recovery | Durable connector/Companion/worker paths have focused tests and documented mechanisms, but [v1-commercial-viability-gap-audit.md](v1-commercial-viability-gap-audit.md) finds no unified retained attempt history or three-path failure exercise. | Induce one unavailable client and one transient delivery failure; diagnose, recover, and verify no duplicate/lost canonical message or wrong-identity post. |

## Proposed release-gate exercise (not yet executed)

1. Install a checksummed, immutable application artifact in a clean environment; record artifact, migration, client, OS, browser, and plugin/Companion versions.
2. Bind one web human, one protected Codex profile, one current-flow ChatGPT discussion, and one Gemini discussion; test an independent remote MCP client only after its generic context contract is frozen.
3. Have the human address Codex, Codex reply and address ChatGPT, and ChatGPT reply and address Gemini. Compare message IDs, project sequence, addressees, reply links, and acknowledgement records from the canonical API after each step. This supplies more than the minimum three independent paths.
4. Repeat a broadcast and negative cross-project/unbound/revoked identity case. Interrupt one client, recover delivery, and verify the same canonical outcome without duplicate posts or premature acknowledgements.
5. Record exact outcomes and known limitations per surface. Until then, P0.7 and the Phase 0 cross-provider gate remain open.

The 2026-09-16 [Docker acceptance record](docker-acceptance-2026-09-16.md) proves clean source-tree startup, migrations, health, and backup/restore. It explicitly does **not** prove an immutable-release install, provider handoff, upgrade, or rollback.
