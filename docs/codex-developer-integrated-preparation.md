## One proposed preparation path

`IntegratedPreparation` composes the existing DeveloperBAdapter with:

1. `CanonicalAuthority`: compares the canonical request and owner approval-event
   relationship, protected profile/server/project/participant, exact reviewed
   request material/body, positive responsibility event/owner/request ID and
   explicit plan/time/interruption bindings. Deleted/edited/changed/unavailable/
   wrong-owner/profile/context approvals stop. Seen/ack timestamps are observation
   metadata, not authority material. The source parser uses the existing message
   shape; it does not introduce a server reservation service.
2. `SessionStorage`: one continuously held existing-container session contract,
   matching the validated Windows callback/file manifest. The FULL manifest
   (paths, normalized names, identities, lengths, ACLs, namespace and dimensions)
   is pinned to the native preparation context and checked on every operation.
   Its compact projection also binds the fixed journal. No create/resize/rename
   or directory publication is used.
3. `FixedJournal` plus `FixedPreparationJournal`: permanent reservation, canonical
   receipt/observation records, bounded multipart evidence with final logical
   commit, fixed record/head slots, file flush/readback and caller-retained head
   compare-and-advance. Partial/occupied/capacity/identity/authority/handoff failure
   stops terminally. Evidence and failed slots remain; no reconstruction/replay.
4. The actual preparation state machine: retained pre-suppression observation,
   intent, fresh owner/time admission AFTER evidence writes, modeled exact
   suppression, preserved postimage/before-stop anchor, fresh stop admission,
   independent quiescence, cutoff capture and frozen command-boundary evidence.
   Every outcome still sets authorizes_install=false. No install/activation
   command exists in this integration.
